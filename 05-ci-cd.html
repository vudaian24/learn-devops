Bước 05

CI/CD cho DevOps

Tự động hóa từ lúc commit code tới lúc chạy trên production — giảm lỗi con người, rút ngắn thời gian phát hành. 11 phần đi từ khái niệm, GitHub Actions, đến chiến lược deploy an toàn.

01 CI/CD là gì

CI/CD là chuỗi tự động hóa biến một lần git push thành một bản chạy được trên production, qua các mức độ tự động khác nhau.

Khái niệmMô tả
Continuous Integration (CI)Tự động build & test mỗi lần code được push, phát hiện lỗi ngay thay vì dồn tới cuối sprint.
Continuous DeliveryTự động chuẩn bị một bản release luôn sẵn sàng deploy — nhưng bước deploy cuối cùng cần người bấm nút duyệt.
Continuous DeploymentTự động deploy thẳng lên production ngay khi pipeline pass, không cần con người can thiệp.
Phân biệt nhanh: cả 3 đều tự động build/test; khác nhau ở việc bước cuối "lên production" có cần người duyệt hay không.

02 Git workflow làm nền cho CI/CD

Pipeline được kích hoạt bởi sự kiện Git — hiểu rõ trigger nào chạy gì giúp thiết kế pipeline hợp lý và tiết kiệm chi phí CI.

Sự kiệnThường dùng để
push lên branch featureChạy lint + unit test nhanh, phản hồi sớm cho developer.
pull_requestChạy toàn bộ test suite + security scan trước khi cho phép merge.
push lên mainBuild image, deploy tự động lên staging.
push kèm tag (ví dụ v1.2.0)Đánh dấu một release chính thức, deploy lên production. Không có event riêng tên "tag" — vẫn là push, lọc bằng tags:.
schedule (cron)Chạy job định kỳ: quét bảo mật, dọn dẹp, backup.
manual (workflow_dispatch)Cho phép người vận hành chủ động bấm nút chạy khi cần.

03 Anatomy của một pipeline

Một pipeline điển hình gồm các stage nối tiếp nhau, dừng ngay nếu một stage fail (fail fast).

Thứ tựStageMục đích
1CheckoutLấy code từ Git về máy chạy CI (runner).
2Install dependenciesCài package, thường có cache để tăng tốc lần chạy sau.
3LintKiểm tra style code, phát hiện lỗi cú pháp sớm và rẻ nhất.
4Unit testTest từng phần logic độc lập, chạy nhanh.
5BuildCompile hoặc bundle ứng dụng.
6Security scanQuét lỗ hổng dependency/code/image (xem mục 07).
7PackageĐóng gói thành Docker image hoặc artifact.
8Push registryĐẩy artifact lên nơi lưu trữ để bước deploy lấy về.
9Deploy stagingTriển khai tự động lên môi trường staging để kiểm thử.
10Integration testTest toàn hệ thống trên môi trường giống thật.
11Deploy productionTriển khai lên production, thường có cổng duyệt thủ công.

04 GitHub Actions cơ bản

GitHub Actions định nghĩa pipeline bằng file YAML đặt trong .github/workflows/.

TrườngMô tả
nameTên hiển thị của workflow.
onSự kiện kích hoạt (push, pull_request, schedule...).
jobsNhóm các job, mỗi job chạy trên một runner riêng, mặc định song song.
runs-onLoại máy chạy job (ubuntu-latest, self-hosted...).
stepsDanh sách bước tuần tự trong một job.
usesDùng lại một action có sẵn (viết bởi cộng đồng hoặc chính bạn).
runChạy trực tiếp một lệnh shell.
env / secretsBiến môi trường thường và biến nhạy cảm (xem mục 10).

05 Ví dụ pipeline GitHub Actions đầy đủ

Build, test, và đẩy Docker image lên registry mỗi khi push vào main.

name: CI

on:
  push:
    branches: [main]

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Node
        uses: actions/setup-node@v4
        with:
          node-version: "20"

      - name: Install & test
        run: |
          npm ci
          npm test

      - name: Log in to registry
        run: |
          echo "${{ secrets.DOCKERHUB_TOKEN }}" | docker login -u ${{ secrets.DOCKERHUB_USER }} --password-stdin

      - name: Build & push image
        run: |
          docker build -t myrepo/api:${{ github.sha }} .
          docker push myrepo/api:${{ github.sha }}
Tag image bằng github.sha (mã commit) thay vì latest — mỗi lần build ra một artifact định danh rõ ràng, dễ truy vết và rollback.

07 Build & test tự động

Càng phát hiện lỗi sớm trong pipeline, chi phí sửa càng thấp — đây là lý do stage rẻ (lint) luôn chạy trước stage đắt (build, deploy).

Loại kiểm traMô tảVí dụ công cụ
LintKiểm tra style/cú pháp code.ESLint, tflint (cho Terraform)
Unit testTest từng hàm/module độc lập.Jest, pytest, go test
SAST (Static Application Security Testing)Quét mã nguồn tìm lỗ hổng bảo mật mà không cần chạy ứng dụng.Semgrep, CodeQL
Dependency scanQuét thư viện bên thứ ba có lỗ hổng đã biết (CVE).Dependabot, Snyk
IaC scanQuét file Terraform tìm cấu hình sai/không an toàn — áp dụng trực tiếp cho repo của bạn.tfsec, checkov

08 Đóng gói & đẩy artifact

Kết quả build cần được đóng gói thành một đơn vị bất biến, có version rõ ràng, để mọi môi trường đều chạy đúng một bản.

BướcMô tả
Build imageBuild Docker image từ Dockerfile (xem Bước 3).
Gắn tag phiên bảnDùng git SHA hoặc semantic version (v1.4.0), không dùng latest.
Đẩy registryPush lên Amazon ECR, Docker Hub, hoặc GitHub Container Registry.
Quét trước khi deployQuét lỗ hổng image (Trivy) ngay trong pipeline trước khi cho phép deploy.

09 Chiến lược Deployment

Chiến lượcMô tảĐánh đổi
RecreateTắt hết bản cũ rồi mới chạy bản mới.Đơn giản nhất nhưng có downtime.
Rolling updateThay dần từng instance cũ bằng instance mới.Không downtime, nhưng có lúc cả 2 version cùng chạy song song.

CanaryCho một tỷ lệ nhỏ traffic dùng thử version mới trước khi mở rộng dần.An toàn nhất, nhưng cần theo dõi metrics kỹ (xem Bước 6).

10 Quản lý secrets trong CI/CD

Pipeline cần quyền truy cập nhạy cảm (registry, cloud) — quản lý sai cách là nguồn rò rỉ phổ biến nhất.

Khái niệmMô tả
GitHub Actions SecretsLưu secret mã hóa ở cấp repo/organization/environment, không hiện trong log, inject qua secrets.*. Secret ở cấp environment còn có thể yêu cầu reviewer duyệt trước khi job được đọc.
GitLab CI/CD VariablesTương đương secrets của GitLab, có thể giới hạn theo branch/environment.
OIDC federationCI runner lấy quyền tạm thời từ AWS IAM Role qua token OIDC — không cần lưu access key dài hạn nào trong CI.
Không bao giờ echo hay print giá trị secret trong step log — nhiều CI hệ thống tự động mask, nhưng không phải lúc nào cũng đáng tin cậy 100%.

11 Best practices

  • Fail fast: chạy lint/unit test rẻ trước, để stage tốn thời gian (build, deploy) chỉ chạy khi cần.
  • Cache dependency (node_modules, pip cache) để rút ngắn thời gian chạy pipeline.
  • Pin version cụ thể cho action/base image, không dùng @latest hay @main.
  • Bắt buộc PR review + status check pass trước khi merge vào branch chính.
  • Tách rõ approval gate giữa staging (tự động) và production (cần người duyệt).
  • Luôn có kế hoạch rollback rõ ràng — biết chính xác lệnh nào để quay lại version trước.
  • Dùng OIDC thay vì access key tĩnh khi CI cần gọi tới cloud provider.
